# Risks, limits and open questions

Four lists. **Q, settled**: points where the plan had to interpret or narrow
a fixed decision, with the coordinator's decision. **Q, open**: points still
waiting for one. **K**: limits the design
accepts knowingly. **T**: technical risks, each tied to the spike or test
that settles it.

## K. Known limits

| Id | Limit | Consequence |
| --- | --- | --- |
| K-1 | A group works only while its home is on and reachable, and the home holds the only copy (Q-12). | Stated to the user at creation and on the computers page (R-134). |
| K-2 | A browser cannot open a connection without some signalling path: a rendezvous service, or a node on the same machine. Two devices behind NAT on different networks cannot find each other while no rendezvous is reachable. | "Works without the server" means: open connections continue, nodes on one network or with a reachable remembered address reconnect, and a local browser works through its local node. |
| K-3 | An inbox item is written to a session at most once. A node that stops after recording the delivery and before writing the turn loses that turn. | The home's quiet-task notice brings the secretary to it (`flows/task.md` H). No redelivery machinery. |
| K-4 | Device log: two entries for one version make a fork, and receivers may disagree. It happens when a stolen device and its owner race to revoke each other, and when two devices of one person each add a device at the same moment. | Guidance: add one device at a time. Recovery is manual. Not designed in step 1. |
| K-5 | Signalling envelopes older than two minutes are dropped. | A device with a badly wrong clock cannot connect; the error says so. |
| K-6 | The node cannot stop the owner from resuming a session id in their own terminal outside SoloDawn. Two writers lose messages `[verified]`. | Stated in the documentation and on the terminal page. |
| K-7 | Usage figures are whatever each CLI reports. | The card shows what exists. |
| K-8 | In step 1, check commands run on the assignee's machine with the owner's rights, outside any sandbox, and what they execute is the task's code (Q-19). | They get a minimal environment; the interface says what level 2 does and does not limit. Step 2 moves checks into an operating-system sandbox and adds per-owner acceptance of the command list. |
| K-9 | Home and clients do not verify each other's software version beyond the protocol number. | A protocol change bumps `v`; old clients are told to update. |
| K-10 | (Removed in round 1: the secretary's terminal is read only, see Q-20.) | — |
| K-11 | When a task is given to another AI, uncommitted changes of the previous one are discarded with its worktree. | Committed (and pushed) work carries over. |
| K-12 | The outbound secret check is a short pattern list. It catches accidents, not intent. | Stated as such; no configuration. |
| K-13 | A new task session knows nothing of earlier tasks except the notes it is given and what it reads in the group. | The secretary is instructed to write lessons as notes (R-102). |
| K-14 | A merge is an action outside the system and cannot be taken back. A person's cancel that arrives while the host is merging leaves the change merged under a cancelled task. A node that stops in the middle of a merge reports, when it restarts, what it finds: merged, or a conflict. | Stated on the cancel confirmation for a task at step `merge`. No retry, no rollback (R-24). |
| K-15 | The list of weak keys (`contracts/envelope.md` section 2) stops the fourteen encodings of small-order points and nothing more. A key that is a real key with a small-order point added to it, or a signature whose first half is such a sum, passes the list, and Ed25519 libraries may disagree on whether such a signature verifies. Telling these apart needs a multiplication on the curve, which WebCrypto does not offer. | No rule. Such a key enters a log only when a valid device of that person adds it, or a holder of the pairing secret pairs it; what it can cause is that person's devices disagreeing about an envelope, as in K-4. Frontend task F-01c may run one such case to observe what each browser answers, without asserting it. |
| K-16 | Go's JSON decoder refuses more than 10,000 levels of nesting; browsers have other limits. A payload nested that deep could be read by one implementation and refused by the other. | No rule. Only the signer of a payload can write one. |
| K-17 | A JSON string may hold the escape of a lone surrogate (`"\ud800"`). Go reads it as U+FFFD; a browser keeps the surrogate. Ids cannot hold one (`contracts/conventions.md` section 2), but free text can: a message, the name of a device. | No rule. The node and the browser then hold different characters for that text; signatures and the pairing `mac` still agree, because a browser turns a lone surrogate into the same three bytes when it encodes the text. Only the signer of a payload can write one. |
| K-18 | A number that is not an integer, such as a usage percentage, can be written `1e400`: Go refuses the payload and a browser reads infinity. | No rule. No honest sender writes it, and no such field is on a path that authenticates anything. |
| K-19 | A forward or mapping to a node's UDP port benefits only the connections it answers (`contracts/rendezvous.md` section 5.1, point 8). When the node that offers is the one that can be reached, and the other direct UDP and IPv6 paths fail, the direct path left is TCP from the answering node to the offering node's port 47801: verified between two pion nodes on Linux, `[unverified]` through a router's mapping. Otherwise the relay. | Spike S-8 verifies the mapping, reachability from outside and publication of the external port. A group's home is meant to be the machine that can be reached (K-1). |
| K-20 | Safari deletes everything a site has stored, IndexedDB and the browser's device key with it, after seven days of Safari use without a visit to the site. A web app added to the home screen is exempt (`docs/decisions/implemented/architecture/2026-11-20-browser-baseline.md`). | That browser comes back as a new device and is paired again (`flows/pairing.md` C); the owner revokes its old entry. After pairing the client asks the browser to keep its storage (`navigator.storage.persist()`), which Safari grants by rules of its own, and the settings page explains adding the app to the home screen (frontend tasks F-04, F-13). |
| K-21 | An approval shows only the first 3 KiB of the command (`contracts/messages.md` 2.3), and nobody can read the rest: the node keeps the digest of the whole request and the part shown, not the full text, and taking over the terminal interrupts the request. The owner may approve having seen a part only. | The card says that it shows a part and how long the whole is. When a request cannot be seen in full, the recommended action is to deny it and ask the AI to split it into smaller steps; the card says that too. A decision covers the whole request, whose digest the host recorded. Later enhancement, not in the first version: the node stores the full text and the person can view it. |
| K-22 | A message is short. How short, and why, is in `contracts/rows.md` section 5. | Accepted for the first version; a longer text is sent as several messages. Looked at again in step 2 or 3 if it proves too little. |
| K-23 | A node closes a signer's previous inbound connection on that signer's next ordinary offer (`contracts/rendezvous.md` 2.3), so two browser tabs that share one device key share one inbound slot on a node. | Resolved by the one-active-tab rule (Q-28, `flows/connect.md` F). What remains is the other case of section 5.1, point 4, there: a NAT can give an endpoint to a different device while the node still holds the old connection, and closing by signer cannot clear that registration. No rule in the first version; recovery depends on which candidates can be checked (`contracts/rendezvous-evidence.md`, entry 4). |

## Assumptions that would change the design if false

1. A group has at most a few dozen members and a few hundred open tasks, so
   a home keeps all state rows in memory.
2. One node hosts at most a handful of open sessions at a time.
3. Messages are text of a few kilobytes; nothing binary travels in groups.
4. The owner's Git and `gh` are already signed in on every machine that
   runs an AI.
